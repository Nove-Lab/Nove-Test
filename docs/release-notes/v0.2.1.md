# v0.2.1 — the standalone binary can run pytest projects again

Released: 2026-07-22

A **patch release with one headline fix**. If you installed novetest as the
standalone binary (`curl … | sh` / `irm … | iex`), v0.2.0 could not run **any**
pytest project — every run stopped at `engine-misconfigured` (exit 4) before a
single test executed. v0.2.1 fixes that. No wire-schema change, no exit-code
reclassification.

## The fix: readiness probes the interpreter that actually runs your tests

novetest resolves the pytest interpreter **venv-first**: a workspace `.venv` if
it has one, otherwise the interpreter running novetest. Readiness, however, was
hard-coded to probe novetest's *own* interpreter (`sys.executable`).

Under the standalone binary those are not the same thing. The binary bundles a
**sealed** python-build-standalone CPython that can never carry pytest, so
readiness looked for pytest in the one interpreter guaranteed not to have it,
and failed the run *before* venv-first resolution ever got a chance. The
remediation it printed — `pip install pytest` — pointed at that same sealed
interpreter, which cannot be installed into. Readiness now resolves the
interpreter **once**, through the same resolver the adapter uses, and probes
that one. Whatever readiness declares ready is what actually runs.

**Were you affected?**

| Install method | v0.2.0 status |
|---|---|
| Standalone binary (`curl … \| sh`, `irm … \| iex`) | **Broken** — no pytest project could run |
| `pip install novetest` into a venv | Unaffected (when pytest is in that same venv) |
| `pipx install novetest` | Unaffected only if the SuT has its own `.venv` |
| `uv tool install novetest --with pytest --with pytest-json-report` | Unaffected |

The pip/pipx/uv paths were not hit in the common case because novetest's own
interpreter usually *did* have pytest importable. The binary never can.

## What a Python project needs

**A `.venv` in your project carrying `pytest` and `pytest-json-report` is what
a binary install resolves against**; without one, novetest falls back to its own
interpreter (which, for the binary, has neither). Resolution is exactly two
tiers — workspace `.venv` → novetest's interpreter. There is deliberately **no
bare-`pytest`-on-PATH tier**.

Add `pytest-cov` as well: readiness itself gates only on pytest and
pytest-json-report, but `novetest test` collects coverage by default and needs
`pytest-cov` to complete. The remediation now names all three, so following it
verbatim gets you to a green `novetest test` in one step:

```
python3 -m venv .venv && .venv/bin/python -m pip install pytest pytest-json-report pytest-cov
```

On Windows: `py -m venv .venv && .venv\Scripts\python -m pip install pytest pytest-json-report pytest-cov`.

A misconfigured workspace now reports which interpreter was probed, rather than
an un-actionable install hint:

> pytest is not importable from the resolved interpreter (`<interpreter>`);
> install pytest, pytest-json-report and pytest-cov into `<workspace>/.venv`
> (novetest prefers the workspace's own .venv over its interpreter; pytest-cov
> is what the coverage-collecting verbs such as `novetest test` additionally
> need) — from `<workspace>` run: `python3 -m venv .venv && .venv/bin/python -m
> pip install pytest pytest-json-report pytest-cov`

## `engine_version` now reports the pytest that ran

The Run Record's `engine_version` is read from the **resolved** interpreter. If
your project `.venv` runs pytest 9.1.1 while novetest's own environment has
9.0.3, the record now says `9.1.1` — the version that actually executed the
suite. Previously it reported novetest's own copy, so stored evidence could
name a pytest that never ran.

## Also in this release

- **Docs reconciled to the venv-first truth.** `docs/agent/languages.md` and
  `docs/human/languages.md` (plus both `troubleshooting.md` files, which quoted
  the old strings verbatim) drop the stale `<sys.executable> -m pytest` /
  "importable from the interpreter that runs novetest" claims and state the
  two-tier resolution order.
- **A release gate that would have caught this.** `release-test.yml` previously
  exercised the built binary with `--version` only — no gate in the project
  could have detected the defect. It now runs the real binary against a pytest
  project with a `.venv` and asserts the suite actually executes and reports the
  right `engine_version`, plus the venv-less boundary case. Verified to fail
  against a v0.2.0 build.

## Compatibility

**No schema change** — the envelope is still `novetest/v1`, and no exit code was
reclassified. Exit 4 for a genuinely unusable engine is unchanged; what changed
is that a **working** setup is no longer misclassified as broken. Nothing in
v0.2.0's breaking-adjacent list is revisited, so if you already upgraded to
v0.2.0 there is nothing new to audit.

## Upgrading from v0.2.0

Re-run the install one-liner for your platform; it overwrites the binary in
place. The on-disk Project Store needs no migration. If you previously worked
around the defect by installing novetest via pip/pipx instead of the binary,
that workaround remains valid — the binary is simply usable again.
