# v0.3.0 — the Linux binary starts on normal Linux again

Released: 2026-07-30

**One headline fix, plus behaviour changes worth reading before you upgrade.**
Every novetest Linux binary ever published — `v0.1.1`, `v0.1.2`, `v0.1.3`,
`v0.2.0`, `v0.2.1` — required **glibc 2.39** and refused to start on anything
older. That excluded Debian 11 and 12, Ubuntu 20.04 and 22.04 LTS,
RHEL/Rocky/Alma 9, Amazon Linux 2023, Fedora 39, and the Debian 12 base of the
official `node:*` images. v0.3.0 lowers that requirement to **glibc 2.31**.

The JSON envelope schema is still `novetest/v1` and no exit code was
reclassified. But this is a **minor** release rather than a patch because
**output shapes moved**: fault localization ranks differently, `recommendations[]`
is ordered by rank, `--help` / `<verb> --version` / usage errors emit the
envelope in JSON mode, and on Windows a persisted coverage path changed value.
Read **Breaking changes** and **Compatibility** below before upgrading.

## The bug: a build-host detail became a runtime requirement

The failure had nothing to do with novetest's Python. It happened in the dynamic
loader, in about five milliseconds, before a single line of Python ran:

```
novetest: /lib/x86_64-linux-gnu/libc.so.6: version `GLIBC_2.39' not found
  (required by .../novetest)
```

A glibc-linked binary can run on any glibc **at least as new** as the one it was
built against, and never on an older one. The release pipeline built the Linux
binaries on its CI runner, and that runner's image had moved to Ubuntu 24.04
(glibc 2.39) — so the floor moved with it, silently, for every release. Nothing
in the pipeline could notice: every job that ran the binary ran it on the same
modern machine that had just built it.

v0.3.0 builds the Linux binaries inside a **Debian 11 "bullseye"** container
(glibc 2.31) instead. The runner is now only a choice of CPU architecture. The
macOS and Windows binaries are built exactly as before and are unaffected.

## Supported minimum: glibc 2.31

**The Linux binary requires glibc 2.31 or newer.** Check your host with
`ldd --version`. That number is a guarantee, not an observation: CI fails the
build if a Linux binary ever requires a version symbol above it. The v0.3.0
binary as shipped in fact requires only `GLIBC_2.30`, so a 2.30 host works
today — but 2.31 is the version to plan against.

| Host | glibc | v0.2.1 | v0.3.0 |
|---|---|---|---|
| Debian 12 "bookworm" (incl. official `node:*` images) | 2.36 | broken | **works** |
| Debian 11 "bullseye" | 2.31 | broken | **works** |
| Ubuntu 22.04 LTS | 2.35 | broken | **works** |
| Ubuntu 20.04 LTS | 2.31 | broken | **works** |
| RHEL / Rocky / Alma 9 | 2.34 | broken | **works** |
| Amazon Linux 2023 | 2.34 | broken | **works** |
| Fedora 39 | 2.38 | broken | **works** |
| Ubuntu 24.04, Debian 13, Fedora 40+ | ≥ 2.39 | works | works |
| Debian 10, RHEL / CentOS 8, Ubuntu 18.04, Amazon Linux 2 | ≤ 2.28 | broken | still unsupported |

Debian 11 and 12, Ubuntu 20.04/22.04 and Fedora 39 were exercised end-to-end
with the real release artifact; the rest follow from the binary's symbol
requirements. Hosts below the supported minimum remain out of reach for the
standalone binary — `pip install novetest` (or `uv tool install novetest`) has
no glibc floor of its own and stays the supported path there.

Note that the CPython that PyApp downloads on first run is *also* glibc-linked;
it needs only glibc 2.17, so the binary itself is what sets the floor.

## Two CI guards so the floor cannot rise again silently

- **A symbol-floor assertion** runs immediately after each Linux binary is
  wrapped. It reads the `GLIBC_x.y` version symbols out of the artifact and
  fails the build if the highest one exceeds a pinned ceiling (currently 2.31).
  Run against the published v0.2.1 artifact it fails, naming `GLIBC_2.39` — the
  defect this release fixes would not have shipped.
- **An old-glibc runtime smoke** runs the real artifact inside `debian:11`
  (glibc 2.31 — exactly the supported minimum above), `debian:12` and
  `ubuntu:22.04` containers with a fresh `HOME`, so PyApp's first-run CPython
  download happens there too, and asserts an `ok: true` `novetest/v1` envelope.
  This is the half that proves the *whole* chain — binary plus downloaded
  runtime, dependencies included — actually starts, and it is exercised at the
  published floor rather than merely above it.

Both gate the release job, so a binary with a risen floor can no longer reach
the release feed. The `linux-aarch64` binary gets the same build baseline and
the same symbol assertion; its runtime smoke is x86_64-only for now (running an
arm64 container on the x86_64 release runner would need emulation).

## ⚠ Breaking changes

### Windows: Coverage Facts stored before v0.3.0 no longer join against new ones

Coverage Facts derived on **Windows** by v0.2.0 / v0.2.1 recorded `file_path`
with backslashes (`src\pkg\calc.py`). From v0.3.0 every platform records
`src/pkg/calc.py`, matching the paths that test node ids and fault-localization
results already used. `novetest coverage diff` and `novetest compare` join two
runs on exactly that field, so a comparison that **straddles the upgrade** finds
nothing in common on either side.

Here is what a Windows user actually gets, at exit code **0**:

```json
{"ok": true, "warnings": [],
 "data": {"coverage_delta": {
   "files_added":   ["shared_defect/totals.py", "tests/test_totals.py", "..."],
   "files_removed": ["shared_defect\\totals.py", "tests\\test_totals.py", "..."],
   "file_deltas":   [],
   "summary_before": {"percent_covered": 100.0},
   "summary_after":  {"percent_covered": 100.0}}}}
```

Every file is reported as simultaneously removed and added, `file_deltas` is
empty so no line-level change surfaces at all, and the coverage summary looks
perfectly healthy — with `ok: true`, **zero warnings**, and exit 0. novetest
cannot distinguish this from a genuine mass rename, so it does not warn you.
**That silence is why this has its own heading:** a consumer reading that
envelope concludes the entire codebase was rewritten, and nothing in the output
says otherwise.

**Recovery.** Re-run the tests for the older side under v0.3.0 and compare
against that fresh run. The stored side cannot be repaired in place: Coverage
Facts are derived only while a run executes, and `novetest coverage show` is a
cache read that never re-derives.

**Scope.** Windows only, and only a `coverage diff` / `compare` whose two runs
straddle the upgrade. A comparison where both sides were produced by the same
version is unaffected, as is every store created on Linux or macOS.

## Also in this release

- **Fault localization no longer ranks the run's own test functions, and it now
  shows you what it removed.** A suspect is dropped from the ranking only when it
  *is* a test function discovered in that run — matched by file **and** symbol
  against the Run Record's own node ids, never by a name heuristic. Three shapes
  change: a file holding both product code and its tests keeps its production
  symbols (previously the whole file was dropped, taking the real defect with
  it); a monorepo whose pytest `rootdir` sits above the project is filtered at
  all (previously the two path spellings never matched and nothing was excluded —
  on the reference project the top suspect moved from
  `tests/test_totals.py::test_total_percentage_discount_with_tax` to
  `shared_defect/totals.py::invoice_total`, and `recommendations[0]` moved with
  it); and a mistake that really is in the failing test is now reported rather
  than silently deleted. `localization_outcome.metadata` gains **four** keys:
  `test_file_locations_excluded`, `test_file_exclusion_reverted`,
  `test_file_exclusion_basis` (`"exact"`, `"path_suffix"` or `"none"`) and
  `test_file_locations_suppressed` (the removed locations that scored above zero,
  best first, capped at three, each carrying a `score_raw` on the selected
  formula's scale so it compares directly against `entries[*].score_raw`). On an
  older build these four keys are **absent** rather than `null`, so a consumer
  that pins the envelope shape will see keys appear. **Known limitation:** when
  the mistake really is in a failing test that also exercises product code, the
  ranking still leads with that product code — the engine cannot tell that apart
  from the structural bias it corrects, so it reports the suppressed test symbol
  alongside instead of guessing.
- **`recommendations[]` is ordered by rank, then score.** Within a priority and
  category the array now follows the analysis's own confidence ordering
  (`slots.rank` ascending, then `slots.score_normalized` descending) instead of
  falling straight through to the file path. The objects themselves are
  unchanged and `recommendation_schema_version` is still `1` — only the order
  moved. For a consumer, the honest reading is that `recommendations[0]` is now
  **the analysis's top-ranked suspect**, which is a weaker claim than "the
  defect": when several suspects tie on both rank and score, the order among
  them is still decided by file path, so consider **every recommendation sharing
  `recommendations[0].slots.rank`** rather than position 0 alone.
- **`--help`, `<verb> --version` and usage errors now emit the `novetest/v1`
  envelope in JSON mode.** Under `NOVETEST_OUTPUT=json` (or `--output json`),
  `novetest <verb> --help` returns `ok: true` with `command: "help"` and a
  structured `data` block (`commandPath`, `usage`, `summary`, `description`,
  `parameters[]`, `subcommands[]`); `novetest <verb> --version` returns the
  standard identity envelope; and an unknown option, a missing argument or a
  value the parser cannot coerce (`--top-n abc`) returns `ok: false` with a
  machine-readable `errors[0].code` drawn from `unknown-option`,
  `unknown-command`, `missing-argument`, `invalid-value`, `unexpected-argument`
  and `usage-error`. **This breaks anything that parsed
  those surfaces as text in JSON mode, and fixes anything that piped them to a
  JSON parser** — previously they emitted formatted human text and no envelope at
  all. Two details worth pinning: the envelope goes to **stdout**, where the
  human-formatted error block went to stderr; and the exit codes are unchanged
  (`0` for help and version, `1` for a usage error). Text mode is byte-for-byte
  what it was. Note the boundary: this covers the *parser's* usage errors. A
  value the parser accepts but the command rejects — `--formula nope`,
  `--top-n 0` — is domain validation, and it stays `invalid-flag` at exit **2**
  exactly as in earlier releases.
- **Coverage `file_path` is POSIX-separated on every platform.** novetest took
  coverage.py's file keys verbatim, and coverage.py renders them in the producing
  host's native separators — so on Windows `CoverageFactSet.file_path` carried
  `\` while node ids and localization results carried `/` for the same file. The
  order of files inside `coverage_facts.json` was platform-dependent too, because
  `\` and `/` sort on opposite sides of the alphabet. Both are stable everywhere
  now. On Linux and macOS this changes nothing; on Windows it changes a persisted
  value — see **Breaking changes** above.
- **The install scripts no longer cite internal planning documents.**
  `scripts/install.sh` and `scripts/install.ps1` referenced roadmap artifacts
  that resolve for nobody outside the project. Their comments and four
  unsupported-platform error messages are reworded; **the installation logic,
  the SHA-256 verification and the exit codes are untouched.** Because the
  scripts are served publicly, their own checksums change with this release —
  if you pin the install script by digest, re-pin it.

## Compatibility

**The wire schema is unchanged.** The envelope is still `novetest/v1`,
`recommendation_schema_version` is still `1`, and **no exit code was
reclassified** — including the new JSON-mode help and usage envelopes, which
keep the exit codes those surfaces already returned.

**Output shapes did move**, in four places:

| Surface | What moved |
|---|---|
| `novetest localization` / `localization latest` | The ranking changed (test functions no longer compete), and `localization_outcome.metadata` gained four keys that are absent — not `null` — on older builds. |
| `data.recommendations[]` (`novetest test`, `novetest run`) | Same objects, new order: rank, then score, then the previous file-path tiebreak. |
| `--help`, `<verb> --version`, usage errors | In JSON mode these now emit an envelope on stdout; previously they emitted none. Text mode is unchanged. |
| Coverage Facts `file_path` | `\` → `/` on Windows. A no-op on Linux and macOS. |

**The on-disk Project Store needs no migration** — no store format, filename or
directory layout changed. The one exception is the Windows separator change
above: `file_path` is a persisted join key, so a cross-version `coverage diff`
or `compare` on Windows produces the misleading delta described under **Breaking
changes**.

## Upgrading from v0.2.1

Re-run the install one-liner for your platform; it overwrites the binary in
place. If you were blocked entirely — the `GLIBC_2.39` loader error above — this
is the release that unblocks you:

```
curl -fsSL https://ailovestesting.com/products/novetest/install.sh | sh
novetest --version
```

**Re-run your tests to get the new analysis.** Localization findings are derived
once per run and then cached under that run id, and the cache is served back
verbatim — so `novetest localization <run_id>` on a run you analyzed before
upgrading returns that run's **old** ranking, without the four new `metadata`
keys and without a warning. Only a fresh `novetest test` / `novetest run` is
analyzed by the new engine. That same re-run is the recovery for the Windows
coverage comparison described under **Breaking changes**.
