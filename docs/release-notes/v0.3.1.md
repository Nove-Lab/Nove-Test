# v0.3.1 — five fixes that were already on trunk, released

Released: 2026-08-05

**No code was written for this release.** v0.3.1 is a re-cut of the `main`
branch as it stood ten commits after the `v0.3.0` tag: five behavioural fixes
that were merged, matrix-CI'd and end-to-end tested between 2026-08-03 and
2026-08-04, plus five documentation/comment commits. This document describes
exactly those ten commits (`v0.3.0..v0.3.1`) and makes no claim about anything
outside that range.

**The wire schema is unchanged.** Still `novetest/v1`, still
`recommendation_schema_version: 1`; no recommendation category was added or
removed, no slot key moved, and the on-disk Project Store needs no migration.

**The release pipeline is byte-identical to v0.3.0.** `scripts/install.sh`,
`scripts/install.ps1` and every file under `.github/workflows/` are unchanged
since the `v0.3.0` tag, so the Linux glibc floor is still **2.31** (same
Debian 11 build container, same pinned PyApp), the PyApp first-run unpack
behaves the same, and — unlike the v0.3.0 upgrade — **an install script pinned
by digest does not need re-pinning.**

**One thing to read before upgrading CI:** a pytest suite whose tests error in
a fixture used to exit **0**. It now exits **3**. Details below.

---

## ⚠ A suite that errors, or never ran, is no longer reported green

Two fixes, one theme. In both shapes the product used to tell an agent "All
tests green; no action recommended" about a suite that had not actually
tested anything.

### 1. A pytest test that ERRORS is now fail-like (exit 0 → exit 3)

pytest reports a setup-time or teardown-time failure through its own
`pytest_report_teststatus` hook as the singular category `"error"`.
`pytest-json-report` writes that string, and the adapter copied it through
verbatim — but `"error"` is not in the fail-like set (`failed`, `errored`), so
the run counted **zero** failures and normalized to `status: "passed"`. A
suite whose fixtures blew up reported `all_green` at **exit 0**.

v0.3.1 adds the outcome-mapping table the pytest path was missing (every other
adapter — jest, go test, cargo — already had one): pytest's `"error"` maps to
`"errored"`, the existing fail-like count then returns `"failed"`, and the run
exits 3.

Measured through the CLI before and after, five shapes:

| Suite shape | v0.3.0 | v0.3.1 |
|---|---|---|
| setup error only | `passed` / exit 0 / `all_green` | `failed` / exit 3 |
| teardown error only | `passed` / exit 0 / `all_green` | `failed` / exit 3 |
| error + passing test | `passed` / exit 0 / `all_green` | `failed` / exit 3 |
| error + genuine failure | `failed` / exit 3 | unchanged |
| all passing | `passed` / exit 0 | unchanged |

**This will turn some currently-green CI jobs red.** That is the fix, not a
side effect: those jobs contain tests that never ran. Nothing else about exit
codes changed — no exit code was redefined; which suites reach exit 3 did.

### 2. A suite that never executed is `unavailable_analysis`, not `all_green`

A collection-time error — a syntax error or a failing module-scope import in a
test file — makes pytest collect nothing. novetest already exited **3** and
already stored `status: "errored"` on the Run Record, but the recommendation
synthesizer never read that field: `match_all_green` gated only on "are there
failed tests?", and a run with zero results has zero failures *by
construction*, so the all-green predicate was vacuously satisfied. The only
signal that anything was wrong was the exit code, and the human-readable
summary actively contradicted it.

`match_all_green` now gates **first** on the run's own status, as an
allow-list (`status == "passed"`), so an unknown future status reads as "did
not execute" rather than "clean". `match_unavailable_analysis` widens
correspondingly, so the run still receives a recommendation naming which
stages could not run. The exit code (3) is unchanged.

Because no frozen `unavailable_analysis` slot can carry *why* the run produced
nothing, a new envelope warning does — see the next section.

`unavailable_analysis`'s summary template also drops its leading "Failing
tests but" clause, which is false in this shape. A deletion, not a rewording:
the remaining sentence is true in both shapes and strictly weaker.

## `warnings[]` gains two codes

`docs/agent/README.md` §5 promises that `warnings[].code` is drawn from a
documented, closed enumeration and tells agents to pin against it. That
enumeration grows from 10 to 12 in this release:

| New code | Source | Emitted when |
|---|---|---|
| `suite-did-not-execute` | orchestration | The suite never ran: `status` outside `passed`/`failed` **and** zero test outcomes. `details`: `run_status`, `executed_tests`, `engine_name`, `ecosystem`. `novetest test` only. |
| `localization-stale-build-rederived` | localization | A cached SBFL finding predates this binary and was re-derived. `details`: `run_id`, `mode`, `missing_metadata_key`, `requested`, `cache_path`. |

Do not confuse `suite-did-not-execute` with the pre-existing
`zero-tests-collected`: the latter means the engine **ran to completion, exited
clean and found no tests** (an explicit target matching nothing). "Never ran"
and "ran, found nothing" are materially different, and `code` is the only wire
surface that separates them. Both catalogs in `docs/agent/` list all 12 codes
as of this release.

## Localization cache: two retrieval-policy fixes

Neither of these changes how a finding is *derived* — the Localization engine
is untouched in this release. Both are about which cached answer you get back.

### `localization latest` with no `--formula` now answers at the defaults

The bare call was history-dependent: `localization latest` → `ochiai`, then
`--formula op2` → `op2`, then `localization latest` again → **still `op2`**.
Same command, same store, an answer determined by what you had asked before
it. The cache-mismatch check was gated on whether the flag was typed, so an
omitted `--formula` could not invalidate a cache derived at another formula.

It now compares the *resolved* values, so a bare call answers at the defaults
(`ochiai`, `top_n 10`) and re-derives if the cache disagrees. Explicit flags
still win over the cache exactly as before, and a matching explicit flag is
still a silent no-op. `details.requested.formula_explicit` /
`.top_n_explicit` continue to disclose whether you typed the flag.

### A pre-v0.3.0 cached finding is re-derived instead of served

A v0.3.0 binary would serve a **v0.2.1** localization ranking back verbatim —
`ok: true`, `warnings: []`, exit 0 — because the derived finding is cached per
run reference with no version component. That reinstated, silently, the
test-file misroute the whole SBFL-exclusion work exists to remove.

v0.3.0 shipped the detector as a sentence in its release notes. v0.3.1 wires
it into the code: an SBFL-mode finding (`sbfl_per_test` / `sbfl_aggregate`)
whose `metadata` lacks `test_file_exclusion_basis` cannot have come from a
v0.3.0-or-newer build — both pipelines render that key unconditionally — so it
is invalidated, re-derived, and reported through the new
`localization-stale-build-rederived` warning. The ranking may **move**, and
that is the point: the old one was the buggy one.

`failure_proximity` findings are deliberately exempt. They never carried those
keys on any build, so their absence says nothing about the cache's age.

### This supersedes part of the v0.3.0 release notes

`docs/release-notes/v0.3.0.md` ("Upgrading from v0.2.1") tells you that a
localization finding derived before the upgrade is served back with the old
ranking, without the new `metadata` keys **and without a warning**. From
v0.3.1 that is no longer true for `novetest localization <run_id>` or
`novetest localization latest` — they detect the stale cache, re-derive, and
warn.

**It is still true for `novetest inspect <run_id>`**, which is a pure cache
read by design and surfaces a pre-upgrade finding silently. Re-running the
tests remains the general remedy, and is the only one that also refreshes
stored Run Records (see **Compatibility**).

## .NET: a conventional `src/` + `tests/` solution is no longer `engine-misconfigured`

Test-project discovery globbed `*.csproj` and `*/*.csproj` only. The other
canonical .NET layout — `src/Foo/Foo.csproj` plus
`tests/Foo.Tests/Foo.Tests.csproj`, which is what `dotnet new sln` conventions
produce — puts every project at depth **2**, so at the solution root the
adapter found no csproj at all: `novetest init` answered
`state: "engine-misconfigured"` and `novetest test` exited **4**, on a
solution that `dotnet test` runs perfectly. The tool found the workspace *by*
its `.sln` and then declined to read it.

Discovery now also reads the projects a root `*.sln` lists, at any depth —
chosen over widening the glob because the solution file is the project list
the user already wrote, exact under any directory naming. Readiness uses the
same function, so `init` and the run agree by construction.

Test-project **selection** gains a tier above the name token: projects
declaring `Microsoft.NET.Test.Sdk` or `<IsTestProject>` win. This is
load-bearing once solutions are read, because a solution also lists sample,
benchmark and tool projects — `samples/TestBed/TestBed.csproj` carries the
`test` token *and* sorts before `tests/`, so a name-only rule picks the sample
and blocks a runnable solution. The tier is framework-neutral, so readiness
still emits its MSTest / NUnit diagnostics for the project you meant.

**Scope, stated because it is easy to over-read:**

- Execution is still one `dotnet test <csproj>`. Whole-solution runs are not
  in this release.
- Per-test coverage attribution for xunit/coverlet is untouched, and **this
  fix does not make .NET fault localization work.** Measured after the fix on
  a nested `src/` + `tests/` xUnit solution: `novetest localization latest`
  still returns zero entries (`sbfl_aggregate`, confidence `medium`). That is
  a separate, known gap.

## An errored test now carries its crash text

Once fix 1 above made an errored suite fail-like, such a run reached fault
localization for the first time — and arrived with nothing to say. The
normalizer mined the `call` phase only, and an errored test's crash is never
there: a **setup** error emits no `call` key at all, and a **teardown** error
emits a *passing* one. Every errored test therefore carried
`failure_reference: null`, on every shape.

v0.3.1 selects the first phase in pytest's own order (`setup`, `call`,
`teardown`) whose own outcome is `failed`, and extracts the same
`crash` → `longrepr` text as before. Order is load-bearing on one measured
shape: a test that fails in `call` **and** errors in `teardown` has two
failing phases, and `call` — the assertion that actually broke — wins.

Measured over 11 report entries (2 canned, 9 from real pytest reports): 4
moved, all of them `None` → crash text on an errored test. The other 7 —
plain call failure, strict-xpass longrepr fallback, compound call+teardown,
passed, xfailed — are identical in outcome, duration and failure reference.

## Documentation and comments

Five of the ten commits change no runtime behaviour, with one bounded
exception noted below. They are listed rather than omitted: a release-notes
document that quietly drops half its commits is the failure mode this project
has already had to correct once.

- **Both agent-facing warning-code catalogs completed** (9 → 12 rows: the two
  codes new in this release, plus `zero-tests-collected`, which the product
  had emitted since before v0.3.0 and no catalog had ever listed), three
  stale `all_green` definitions corrected to carry the new
  `status == "passed"` requirement, and two tables that had stopped rendering
  as tables repaired. *Bounded exception:* this commit also renames the
  `suite-did-not-execute` warning's `details.collected_tests` key to
  `details.executed_tests` (the value counts what **ran**, and on a partial
  collection failure the same record carries `{"collected": 3, "total": 0}`,
  so `collected` was the lying label) and corrects the matching clause in the
  message text. **That warning is new in this release**, so there is nothing
  to migrate: it ships as `executed_tests` and never shipped as anything else.
- **`docs/agent/` and `docs/human/` zero-collected guidance rewritten** around
  the measured envelope shape, replacing an engine enumeration that was false
  by omission and two recipes that read keys the envelope does not have.
- **Two localization source comments corrected** — one that asserted a code
  path was "production-unreachable today" when every Jest project reaches it,
  and one that over-generalized in the other direction by forbidding path
  normalization outright. Three docstrings stop stating as a universal law a
  relation that was measured on one fixture. Comments and docstrings only; no
  executable line changed.
- **README front-page version claim made version-agnostic**, so it cannot go
  stale on a release cut.

The same sweep, run for this release, retired the last version claims that
pinned a specific build as "current" in `docs/agent/install.md`,
`docs/human/install.md` and `docs/human/troubleshooting.md` — including a
SHA-256-mismatch remedy that told users to pin `v0.1.2`, a build with the old
glibc 2.39 floor.

## Compatibility

| Surface | Status in v0.3.1 |
|---|---|
| Envelope schema | `novetest/v1` — unchanged |
| `recommendation_schema_version` | `1` — unchanged |
| Recommendation categories / slot keys | unchanged |
| Exit codes | No code redefined. **Which suites reach exit 3 changed** — pytest error outcomes, above. |
| `warnings[].code` enumeration | **+2 codes.** Consumers pinning the closed set must widen. |
| Project Store on-disk format | unchanged; no migration |
| Linux glibc floor | **2.31**, unchanged |
| `scripts/install.sh` / `install.ps1` | byte-identical to v0.3.0 — a digest pin still matches |

**Stored Run Records are not rewritten by an upgrade.** Normalization happens
while a run executes, so a suite that a v0.3.0 build recorded as `passed`
keeps that status on disk, and reading it back through `memory show` or
`inspect` still shows the old classification. Re-run the tests to get the
corrected one.

## Upgrading from v0.3.0

```
curl -fsSL https://ailovestesting.com/products/novetest/install.sh | sh
novetest --version
```

The install one-liner overwrites the binary in place and is idempotent. Then:

1. **Check any CI job that runs a pytest suite with fixture setup or teardown
   errors.** It exits 3 now. Fix the fixtures rather than pinning back.
2. **Re-run anything you want the new localization ranking for.** A
   pre-upgrade finding read through `localization` / `localization latest` is
   now detected and re-derived with a warning; read through `inspect`, it is
   still served silently.
3. **If you branch on `warnings[].code`, widen for the two new codes** before
   they surface — `suite-did-not-execute` in particular now rides on exactly
   the runs your old build called green.

## Upgrading from v0.2.1 or earlier

Read `docs/release-notes/v0.3.0.md` first — its glibc floor change, its
Windows coverage-path breaking change and its `--help`/usage envelope change
all apply to you, with the one correction noted above under **This supersedes
part of the v0.3.0 release notes**.
