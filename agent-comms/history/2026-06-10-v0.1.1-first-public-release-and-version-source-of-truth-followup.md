## Strategic context

This is the cycle that takes Nove Test from "license + inaugural tag" (v0.1.0, 2026-06-10 morning) to "first public-facing release" (v0.1.1, 2026-06-10 afternoon). The trigger was Manual Test's §"Nit #2" wheel-version-mismatch finding from the v0.1.0 cycle — surfacing that `pyproject.toml::version` was the only thing bumped, leaving the `--version` envelope's `installedVersion` field reporting `"0.0.0"` while the public tag said `v0.1.0`.

The fix was conceptually simple (1-line pyproject.toml bump), but execution revealed an architectural duality: the envelope reads `__version__` from `src/novetest/__init__.py`, which is independently hardcoded — `pyproject.toml::version` is NOT the single source of truth at runtime.

Rather than abort and re-plan, CEO authorized in-cycle scope extension (Option A path) so Release team could ALSO bump the `__init__.py` literal. v0.1.1 shipped successfully. The architectural fix is filed as a Path A decision (`importlib.metadata.version()` migration) executed by Orchestration team in a separate ~20-minute follow-up cycle.

## Load-bearing learnings (4)

### 1. PM brief authoring foot-gun: do NOT assume `pyproject.toml::version` is the single source of truth for runtime version reporting

**Surface**: The v0.1.1 brief at §"File to modify" stated "1-line change: pyproject.toml::version" and at §"Verification BEFORE pushing tag / 4" predicated DoD #5 (`installedVersion: "0.1.1"`) on the pyproject edit alone. This was empirically false on this codebase as of v0.1.1: `__version__` is a separate hardcoded literal in `src/novetest/__init__.py:1`, and the envelope emitter at `src/novetest/orchestration/onboarding/identity.py:38` reads `__version__` directly.

**Why it bit**: The PM brief was authored without auditing the actual source-of-truth pattern, assuming the canonical Python pattern (pyproject = single source of truth). Empirically the codebase was using the "hardcode the literal in two places" anti-pattern — common in early-stage projects pre-PEP 566.

**Mitigation**: Path A decision (this cycle's binding decision) migrates `__init__.py` to `importlib.metadata.version()`. After Orchestration cycle lands, future version-bump briefs CAN safely assume "pyproject is single source" because it will be.

**For future PM briefs (pre-Path A migration)**: any version-bump brief MUST audit both `pyproject.toml::version` AND `src/novetest/__init__.py::__version__` and instruct both bumps. Once Path A lands, this caveat retires.

### 2. CEO Option-A in-cycle scope extension pattern — when to use, when not to

**Surface**: When Release team encountered the brief premise bug, two options existed:
- Option A: extend scope in-cycle (CEO authorizes 1-line src/ edit, slice completes)
- Option B: abort, re-plan, file new brief with corrected scope, re-dispatch

CEO chose Option A. The slice completed in ~10 minutes additional time vs hours for Option B.

**When Option A is appropriate**:
- The scope extension is BOUNDED (single file, single line, no logic delta)
- The bug is in PM brief premise, not in Release execution
- CEO is actively in-conversation and can authorize quickly
- An architectural follow-up is filed simultaneously so the foot-gun closes permanently

**When Option B (abort + re-plan) is appropriate**:
- The scope extension would touch multiple files, multiple teams, or logic-bearing code
- The bug is structural (the slice cannot be cleanly completed even with extension)
- CEO is not available for in-conversation authorization
- The architectural foot-gun cannot be cheaply closed in a follow-up

**Pattern recommendation**: Brief Release team that "if you discover the brief's premise is empirically incorrect, file a question or abort — do NOT silently extend scope. Wait for explicit CEO authorization." The v0.1.1 cycle exemplifies the right shape: Release filed the architectural question synchronously with executing the CEO-authorized extension, preserving the audit trail.

### 3. Manual Test Auto Mode self-direction — works for micro-cycles with strong Release empirical evidence

**Surface**: No formal `agent-comms/verifications/2026-06-10-v0.1.1-*.md` was filed when Manual Test began. Inbox was technically empty. Manual Test self-directed under Auto Mode from the Release handoff's DoD list and the empirical evidence sections, ran the full empirical sweep, filed PASSED findings.

**When self-direction is appropriate**:
- Release handoff cites strong empirical evidence (CI job IDs, SHA-256 byte-identity, multiple independent confirmations)
- The slice is small (single file or few files, single intent)
- The slice's risk profile is low (no new policy decisions, no breaking changes, baseline-maintained)
- A separate verification request would add 30+ minutes of session overhead for a low-information-gain step

**When self-direction is NOT appropriate**:
- Multi-team or multi-file slices where the verification surface is broad
- Slices introducing new policy or contract changes
- Slices where Release evidence is incomplete and requires probing
- Any slice where Main Branch is the appropriate gate-keeper

**Pattern recommendation**: For future micro-cycles matching the safe profile, briefs can include an explicit "Manual Test self-direction OK per 2026-06-10 v0.1.1 cycle precedent" clause. Don't make it default — explicit authorization preserves the option to gate when appropriate.

### 4. PyApp size-stability — identical byte sizes but different SHA-256 across version-only rebuilds

**Surface**: v0.1.0 binary = 6,715,840 bytes / SHA-256 `3d152e7b...`. v0.1.1 binary = 6,715,840 bytes / SHA-256 `f563662a...`. Identical container size, different hash, structurally proves the binary IS the rebuilt 0.1.1 (not a v0.1.0 relabel).

**Why this matters**: For audit / forensics, the PyApp + python-build-standalone wrapping is **size-stable across version-string-only deltas**. The byte-size identity is not a red flag — it's expected. The SHA-256 delta is the proof-of-rebuild.

**Mitigation for future cycles**: when comparing binary integrity across versions, do NOT rely on byte-size delta (will be identical). DO compare SHA-256 (will differ). Manual Test's Scenario K in the v0.1.1 findings is the canonical example of this verification surface.
