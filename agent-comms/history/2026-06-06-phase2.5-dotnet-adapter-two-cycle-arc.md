## Load-bearing lessons (the parts future agents must internalize)

### 1. `dotnet list package` requires restore state that fresh fixtures don't have

The defect: `_probe_coverlet_version` invoked
`dotnet list <csproj> package --include-transitive --format json`
before `dotnet test` (or `dotnet restore`). On a freshly-copied user
project (or canonical integration test fixture, which is freshly
`shutil.copytree`'d every test), the `obj/project.assets.json` file
required by `dotnet list package` does not exist. The command exits 0
(JSON-format succeeds even on the "problems[]" path) but reports
empty `projects[].frameworks[]`, the parser returns `None`, and the
adapter concludes Coverlet is "absent". The adapter then drops
`--collect:"XPlat Code Coverage"` from the argv — no runsettings
generated, no Cobertura emitted, no `coverlet_version` in metadata.

**Why this matters going forward:** any future adapter probe that
relies on `dotnet list package` (or any other command that requires
restore artifacts) MUST either trigger restore first OR move the
probe to after `dotnet test` (which implicit-restores as a side
effect). The pattern bears the same shape as Gradle's
`finalizedBy(:jacocoTestReport)` → `:jacocoTestReport.dependsOn(:test)`
trap from the JUnit cycle: the dependency direction of the underlying
tool dictates timing constraints on adapter probes.

**Fix shape:** F1a — `dotnet restore <csproj>` invocation conditional
on `--coverage` being requested. Non-coverage runs pay zero restore
cost (~50-200ms on warm cache, 1-3s on cold). Restore is idempotent
on already-restored projects.

This is the THIRD adapter cycle where the §2.5 binding gate

masks the defect on developer-equipped hosts.

**Process implication:** §2.5 stays in force through Phase 3 and
beyond. PM continues to dispatch new adapter cycles (or follow-up
fixes that touch adapter integration tests) with §2.5 in the brief.

### 3. Cross-team scope creep manifests as PM-resolvable questions, not silent commits

Hotfix #1's brief §2.2 (F1b) literally required the warning to
"reach the envelope's top-level `warnings` field, not just the
internal payload." Run team's empirical inspection found that no
adapter-emitted warning reaches the envelope top-level today — across
all six adapters — because the `run_cmd` constructs `Envelope(...)`
without a `warnings=` kwarg (only the `localization` handler uses
that field today). Closing F1b strictly would have required touching
`src/novetest/orchestration/workflows/run.py` and
`src/novetest/cli/app.py`, which are Orchestration team territory per
the 2026-05-14 team-structure decision.

Run team's response was textbook: filed
`questions/run-team-2026-06-06-envelope-warnings-projection.md` with
four options (A through D), shipped Option A's metadata-channel
surface in this slice as a Run-team-scope-only partial, and explicitly
called out the cross-team scope creep as the reason. Manual Test
concurred with Option A + Option C in its verdict findings.

PM ratified Option A + queued Option C as MVP-blocking in
`decisions/2026-06-06-adapter-warning-surface-v1-metadata-channel.md`.

**Lesson for future cycles:** when a brief's requirement crosses
ownership boundaries, the originating team SHOULD file a question
rather than silently violating the charter's "Forbidden files" list.
The cost is a partial slice + a follow-up; the benefit is the
boundary stays clean and PM gets explicit signal that a cross-team
slice needs scoping.

### 4. The Cap-X verification capture format is the right shape for adapter cycles

Main Branch's verification doc for the hotfix introduced "Cap-1
through Cap-4" — discrete envelope-capture scenarios with pinned
expected literal values for each capture. Manual Test then
reproduced each Cap-X byte-equivalently (modulo per-run ULIDs +
WSL2-host timestamp strings).

This format is empirically stronger than the prior "scenario list"
approach because:
- Each capture has an explicit set of envelope-field-level assertions
- "Byte-equivalent reproduction" is testable as a binary outcome (vs.
  the older "narrative scenario" style which left room for
  interpretation)
- The Cap-X labels are referenceable in findings (e.g. Manual Test
  said "Cap-4 reproduced; `envelope.warnings == []` matches the
  known-gap reality, not a defect") — this lets PM and CEO trace
  exactly which envelope-shape claim was verified

**Process recommendation:** Main Branch SHOULD continue the Cap-X
format for future adapter verification docs. Manual Test's findings
SHOULD continue the explicit per-Cap reproduction-result table.

### 5. The "single Cobertura file per --coverage" envelope claim is true at API level but understates on-disk reality

Critical edge #8 from the verification doc: "single Cobertura per
`--coverage` invocation." Empirically VSTest's data collector
lifecycle writes Coverlet's output **twice**: once under the
timestamped attachments directory (`_<HOST>_<TIMESTAMP>/In/<HOST>/`)
and once under the GUID per-collector-invocation directory
(`<GUID>/`). Both files are byte-identical (MD5 confirmed by Manual
Test). The envelope's `artifact_paths["coverage_xml"]` correctly
points at exactly one canonical path (the timestamped one), so from
the user's wire-level perspective there IS a single canonical
artifact.

**Doc-precision item (NOT a defect):** future verification docs
SHOULD say "exactly one canonical envelope-bound Cobertura path"
rather than "single file" — the `find` on disk may return N >= 1
byte-identical copies due to VSTest's data collector lifecycle.

### 6. `coverage_outcome.kind` and the dotnet Cobertura derive gap (Coverage-engine follow-up)

A non-hotfix-defect observation surfaced in Manual Test's Critical
edges #1 + #2: even on the post-fix success path (Cap-3) where a
fully-populated Cobertura XML lives at
`artifact_paths["coverage_xml"]`, `coverage_outcome.kind` resolves
to `"unavailable"` — same as the F1b safety-net path (Cap-4). The
user must read `metadata.coverage_unavailable_kind` to disambiguate
"Coverlet absent" from "Cobertura present but Coverage engine can't
derive from it yet".

Root cause: the Coverage engine's `derive_coverage_facts` has a
JaCoCo XML derive path but no Coverlet Cobertura derive path. This
predates the .NET adapter (already on `f8f8d93`); the hotfix didn't
change it.

**Backlog (Phase 3 candidate):** Coverage team implements Cobertura
→ CoverageFactSet derive path so the dotnet adapter's
`coverage_outcome.kind` resolves to `fact-set` consistent with
JUnit/JaCoCo. Estimated scope: small slice, ~3-6h. NOT a hotfix #1
defect; NOT MVP-blocking. PM queues when the cycle pipeline opens up.

### 7. PerTestCoverage = inert (XPlat path) — independently reproduced on second machine

The 2026-06-05 hotfix amendment to the Coverlet decision

The aggregate-effective-default reality is stable; the amendment

### 8. Run team's host-equip detection sequence has a Gotcha

Run team's initial scan on the new machine concluded "host not
equipped for .NET" because:
- `ls ~/.dotnet/dotnet 2>&1 || echo "(missing)"` fired both lines
  due to PATH state, masking that the binary WAS present
- The toolchain shim at `~/.local/share/novetest-toolchains.sh`
  WAS present (1144 bytes) but the initial check's `head -50`
  cut it from view
- `which dotnet` returned nothing because PATH didn't include
  `~/.dotnet`

The actual host-equip state was: dotnet 8.0.421 installed
user-local, Coverlet 6.0.2 cached, toolchain shim present and
self-introspecting. Sourcing the shim
(`source ~/.local/share/novetest-toolchains.sh`) prepended
`~/.dotnet` to PATH and exported `DOTNET_ROOT`, after which the
§2.5 gate ran cleanly (6 passed + 0 skipped + 0 failed in 23.43s).

**Process correction (recorded in WORKLOG #2):** Run team's
host-equip detection sequence MUST be:

1. `source ~/.local/share/novetest-toolchains.sh` (if it exists)
   FIRST.
2. Read the shim's emitted banner — it names exactly what's
   present vs MISSING.
3. Probe each tool via the shim's exported PATH, not via
   `which X` from a default shell.
4. Only conclude "unequipped" when the shim itself reports MISSING
   for the target tool OR when the shim doesn't exist.

The pre-existing scan pattern is too sensitive to PATH state.
