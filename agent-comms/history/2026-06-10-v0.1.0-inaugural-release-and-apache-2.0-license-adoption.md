## Strategic context — why Apache 2.0 + CLA

Decision: `agent-comms/decisions/2026-06-10-license-apache-2.0-with-cla.md`.

The license conversation went through 4 explicit iterations of intent, each driving toward a different license family:

1. **Iteration 1 (CEO frame: protect against competitor embedding)** → recommendation: PolyForm Shield 1.0.0
2. **Iteration 2 (CEO frame: "Apache-like, allow embedding, only block SaaS")** → recommendation shifted to ELv2
3. **Iteration 3 (CEO asks about "Apache 2.0 + Commons Clause")** → PM compared honestly; "Sell" definition is broader and more ambiguous than CEO's intent
4. **Iteration 4 (CEO frame: "block embedding AND derivatives, but allow training/support/research")** → recommendation shifted to AGPL v3 + commercial dual
5. **Iteration 5 (CEO synthesizes: adoption is more important than protection at v0.1.0)** → **Apache 2.0 + CLA selected**

The CLA closes Apache 2.0 §5's "Inbound = Outbound" gap and preserves Nove Lab's unilateral right to relicense future versions under more restrictive terms (BSL / AGPL / proprietary) if a competitive threat materializes after adoption is established. This is the "permissive now, optionality preserved" pattern proven by Confluent / Sentry / Elastic.

The strategic moat for an AI-agent-first CLI is identified as **standard-setting via the JSON envelope schema becoming a de facto convention**, not the code itself. Permissive licensing is the precondition for that path.

## Load-bearing learnings (5)

### 1. Apache plain-text CLA mirror URLs were retired upstream by ASF

The PM brief cited `https://www.apache.org/licenses/cla-individual.txt` and `cla-corporate.txt` as the canonical CLA source URLs. Both URLs now redirect to PDF (`icla.pdf` / `ccla.pdf`) or 404. Release team worked around by extracting CLA text directly from the PDFs.

**Mitigation for future cycles**: pin SHA-256 of a specific ASF PDF snapshot at the time of decision. Add the PDF URL + SHA-256 to the decision doc's "Related sources" section. Pattern: `https://www.apache.org/licenses/icla.pdf` (SHA-256 at adoption-time pinned in the decision doc).

**Decision-doc amendment recommended**: amend `agent-comms/decisions/2026-06-10-license-apache-2.0-with-cla.md` with a "CLA template provenance" subsection that records the exact PDF URL + checksum at the time of v0.1.0 adoption. Optional cleanup; not blocking.

### 2. Draft GitHub Release auth gate vs CDN propagation assumption

The brief's "DoD #14 — Empirical curl-pipe-sh smoke" assumed assets in a draft GitHub Release are CDN-public. They are NOT. Draft release assets are auth-gated to repository collaborators; the canonical `curl -fsSL .../releases/latest/download/...` path returns 404 until the release is promoted to public.

Release team adapted by using `gh release download` (which carries the gh CLI auth token) + serving via a localhost HTTP mirror. The brief's smoke command was modified in-flight; the underlying contract (SHA-256-verified install via the install.sh path) was verified byte-identically against the draft asset.

**Mitigation for future cycles**: brief any "draft-release smoke" as "auth-mirror smoke" explicitly, not "CDN smoke". The fully-public canonical smoke is gated on CEO promotion and is reserved as the post-promotion sanity check.

### 3. Wheel-internal version `0.0.0` mismatch with git tag `v0.1.0` (KNOWN CARRYOVER)

`pyproject.toml::version` was deliberately not bumped in this slice per brief scope. As a result, `novetest --version --output json` reports `installedVersion: "0.0.0"` while the git tag and GitHub Release name are both `v0.1.0`. For users (especially AI coding agents — the intended consumer profile) who parse the envelope output, this mismatch is surprising.

**Status**: documented carryover, not a defect. Manual Test surfaced as nit #2 and recommends a 5-minute Release micro-cycle to bump `pyproject.toml::version` to `0.1.0` + re-run `release-test.yml` BEFORE CEO promotes the draft to public.

**PM disposition**: surfaced to CEO for explicit decision. Two options:
- (A) Run wheel-version-bump micro-cycle first, then CEO promotes — clean user-observable surface
- (B) CEO promotes immediately with `installedVersion: "0.0.0"` carryover, fix in v0.1.1 patch — faster to ship, accepts the mismatch cost

CEO decides per launch timing preference.

### 4. Release team self-merge via "일괄" directive — procedural divergence pattern

CEO's dispatch message included the word "일괄" (batch / all-in-one). Release team interpreted this as authorization to perform FF-merge to `main` themselves rather than handing off to Main Branch team for separate-session merge. This compressed the standard 4-stage cycle (Release → Main Branch → Manual Test → PM) into a 3-stage cycle (Release-with-self-merge → Manual Test → PM).

**When this pattern is safe**:
- Single-team slice (no cross-team merge dependencies)
- Zero `src/novetest/**` and zero `tests/**` modifications (no test gate to re-run)
- File footprint disjoint from any other in-flight worktree
- Explicit CEO "일괄" authorization

**When this pattern is NOT safe**:
- Multi-team parallel slices (need Main Branch as serializer)
- src/tests-touching slices (need test gate from a clean Main Branch checkout)
- Any cycle where the slice's brief explicitly requires Main Branch's verification request as the trigger for Manual Test

**Pattern recommendation**: PM may pre-authorize "Release team self-merge" in future briefs for slices matching the safe profile above by including a one-line explicit clause: "FF-merge to main is authorized within Release team's own session per CEO 일괄 directive precedent (2026-06-10)."

### 5. Hatchling auto-included `NOTICES.md` at PEP 639 path (defensive bonus)

`pyproject.toml::license = { file = "LICENSE" }` instructs Hatchling to embed `LICENSE` in the wheel's `dist-info/licenses/` path per PEP 639. Beyond the spec, Hatchling **also automatically embedded `NOTICES.md` at the same PEP 639 path** because the file lives at repo root next to LICENSE. The wheel now contains both:

```
novetest-0.0.0.dist-info/licenses/LICENSE
novetest-0.0.0.dist-info/licenses/NOTICES.md
```

This is extra hardening for downstream redistributors who only parse `dist-info/licenses/` for compliance — they get both the legal text AND the third-party attribution in one inspection. Pure bonus; not relied on, but should not be regressed in future `pyproject.toml` edits.
