## Load-bearing lessons (the parts future agents must internalize)

### 1. The skip-gate masking class of defects

All three sub-cycle failures shared the same root cause: integration
tests with `shutil.which(<toolchain_cli>) is None` skip-gates ran on
JDK-less / Maven-less / Gradle-less hosts at Run team's pre-handoff
gate, skipped, and never exercised the runtime semantics they claimed
to cover. Concretely:

- **Hotfix-1 Defect 4** (the original CLI-smoke assertion `(0, 1)` bug)
  — assertion never evaluated because the smoke skipped.
- **Hotfix-2 F1** (envelope path `data["run_record"]` vs
  `data["memory_entry"]["run_record"]`) — dereference never evaluated
  because the smoke skipped.
- **Hotfix-2 F2** (Gradle `--continue` not running `:jacocoTestReport`)
  — task-graph semantic never exercised because the integration test
  skipped.

**The structural fix** is `decisions/2026-06-04-equip-and-exercise-for-adapter-cycles.md`
§2.5 (added 2026-06-04 with this cycle's third hotfix queue): when a
Run-team slice modifies `src/novetest/run/adapters/<engine>_adapter.py`
OR `tests/integration/run/test_<engine>_*.py`, the team's **own**
pre-handoff gate MUST run on an equipped host. Skip-gates are not
acceptable on the originating team's gate when the diff touches the
adapter's runtime path.

The amendment paid off **immediately on the very next cycle** (hotfix-3
re-pass): equipped-host gate caught all the same patterns at the
earliest layer, Manual Test passed cleanly, zero JUnit skips at every
gate layer.

### 2. Argv assertions are necessary but not sufficient

Hotfix-2's unit test `TestGradleCoverageArgv::test_continue_present_with_coverage_and_jacoco`
proved `--continue` appeared in argv before `jacocoTestReport`. Argv
was correct. The runtime tool's behavior was not — Gradle's
`--continue` semantic only applies to **independent** tasks, and
`:jacocoTestReport` depends on `:test`. The unit test passed; the real
runtime behavior failed; the integration test skipped on JDK-less host
and didn't catch it.

**Principle:** unit tests pin call shape. Integration tests pin runtime
behavior. When the toolchain's behavior is the unknown, only an
equipped-host integration test answers. Unit tests alone are silent
about runtime semantics.

### 3. Gradle's `--continue` and `finalizedBy` don't help with dependent tasks

When `:test` fails, Gradle's `--continue` only continues **independent**
tasks; `:jacocoTestReport` is dependent and gets skipped.
`finalizedBy(:test, :jacocoTestReport)` also fails to help because the
finalizer's own `dependsOn` (`:jacocoTestReport.executionData(test)` →
implicit task dependency) is unfulfillable.

**The working fix (Fix-D)** is to make `:test` itself tolerate
failures: inject `Test.ignoreFailures = true` on all
`tasks.withType(Test)` via init-script. `:test` reports failures via
JUnit XML but the task-level result is success → graph proceeds →
`:jacocoTestReport` runs → XML emitted. This mirrors Maven's
`-Dmaven.test.failure.ignore=true` and the canonical
"ignore-failures-at-build-tool, derive-status-from-XML-downstream"
pattern. The CLI exit code (3 = `EXIT_USER_TESTS_FAILED`) is derived
from `_aggregate_junit_status` in `normalizer.py:736-757` parsing
the XML, not from the native exit code — so the user-tests-failed
signal is preserved.

The brief had listed Fix-A (two-pass), Fix-B (init-script
`finalizedBy`), Fix-C (fixture edit). Run team's diagnostic walk
showed A + B both fail on Gradle 7.x/8.x/9.x for the same task-graph
reason; Fix-C is rejected by the user-project-assumption rule
("real user builds will not be edited by us"). The actual mechanism
is **Fix-D**, outside the brief's enumeration. Capturing this as a
recurring pattern: **PM lists hypotheses; Run team diagnoses on equipped
host and may surface alternates if reality demands**.

### 4. Per-run hermetic init-scripts

Hotfix-3 writes the Gradle init-script at
`<artifact_dir>/native/init-ignore-test-failures.gradle` (per-run,
under the Project Store), not in `/tmp/` or any process-shared
location. Two properties this preserves:

- **Hermetic** — concurrent runs in the same workspace don't collide
  on a shared init-script path; each run has its own.
- **Postmortem-discoverable** — sits alongside `stdout.log` /
  `stderr.log` / `coverage/jacoco.xml` for retrospective inspection.

This is the model for any future build-tool-side
"generate-config-file-at-runtime" pattern in adapter territory.
Pinned by Run team handoff §4 ("Why under artifact_dir, not /tmp").

### 5. Envelope path consistency across 6 ecosystems

The `novetest run` envelope projects `data.memory_entry.run_record.{...}`
— the `MemoryEntry` carrying the `RunRecord`. CLI smokes asserting
`engine_name`, `summary_counts`, `artifact_paths`, `metadata` etc.
MUST dereference through `memory_entry` first.

Sourcing pin: `src/novetest/orchestration/workflows/run.py:32-46`
(`RunOutcome.memory_entry`) → `src/novetest/cli/app.py:269-281`
(`data = {"memory_entry": entry.to_dict()}`).

Same shape holds for all 6 adapters (pytest, jest, gotest, cargo,
junit, xunit-when-it-lands). Future cycles that backfill CLI-level
smokes for the other 5 adapters MUST use this dereference shape.

### 6. Vendored-asset pattern (first introduced this cycle)

The JUnit Platform Console Launcher (2.8 MB JAR, EPL-2.0) ships
inside our distribution because Java's discovery-only API isn't
exposed via Maven Surefire or Gradle (unlike pytest/jest/gotest/cargo
/dotnet all of which have native discovery CLIs). The pattern:

- `src/novetest/run/adapters/_vendor/<asset>.jar` — the binary
- `src/novetest/run/adapters/_vendor/__init__.py::LAUNCHER_JAR_SHA256`
  — pin for supply-chain integrity
- `THIRD_PARTY_NOTICES.txt` — copyright + license text per EPL-2.0
- `pyproject.toml` `[tool.hatch.build.targets.wheel.force-include]`
  — Hatchling-specific (project uses Hatchling, not setuptools, so
  `package-data` doesn't apply)
- `importlib.resources.files()` — runtime resolution path
- Verified end-to-end by Cap-G in the verification doc (SHA-256
  matches + 2,809,597 byte size)

**Open Q #21** records the **ultimate target**: drop this vendoring
when the `novetest run --list` verb is formally designed, replacing
the vendoring with a JUnit-specific `engine-misconfigured` warning
when the user hasn't installed Console Launcher. This re-aligns
JUnit with the "user installs all native tools" policy followed by
the other 5 ecosystems. **`novetest run` (full execution) is
unaffected** — already routes through user Maven Surefire / Gradle.

### 8. Maven 3.8 vs 3.9 floor mismatch — amendment 2026-06-04

Both Run team's gate host and Main Branch's gate host run Maven 3.8.7
(apt-noble's default; `.claude/settings.json` only pre-authorizes the
apt-install path). The matrix floor was 3.9 — empirically too high.
The JUnit adapter doesn't use any Maven-3.9-specific syntax (`-B`,
`-Dmaven.test.failure.ignore=true`, Surefire 3.x goals all work on
3.8). Floor lowered to **3.8** in this cycle's close commit. Matrix
amendment in `decisions/2026-05-25-supported-engine-matrix.md`,
dev-host doc updated in `scripts/dev-host-setup.md §5`.

## Counter-history (what we DIDN'T do, and why)

- **DID NOT** unwind hotfix-1's Defect-1 + Defect-3 fixes (`reports_dir`
  under store.path + identity parens strip). Each hotfix was
  additive-only; load-bearing prior work stays.
- **DID NOT** mass-backfill CLI smokes to pytest/jest/gotest/cargo.
  The equip-and-exercise §2 binds *new* adapters; retroactive backfills
  are optional. Cargo CLI-orchestration-defect cycle (separate brief,
  unblocked at this cycle's close) covers cargo. Pytest/jest/gotest
  remain on the existing direct-call integration test pattern; future
  retroactive backfill can be queued if needed.
- **DID NOT** queue Fix-A (two-pass), Fix-B (init-script `finalizedBy`),
  or Fix-C (fixture edit) variants of the Gradle JaCoCo fix. Fix-D
  works deterministically across Gradle 7.6 / 8.x / 9.x and matches
  the Maven pattern semantically. No reason to keep alternatives in
  the codebase.
- **DID NOT** introduce a new `AdapterInvocationError.kind` value for
  the Gradle-coverage-skipped case. Hotfix-3 fixes the underlying
  cause; no error kind needed.
