### Deviation from `scripts/dev-host-setup.md`: user-local instead of system

The canonical recipe uses `sudo apt-get install` / `/usr/local/go`
paths. Interactive sudo is unavailable in this Manual Test session
(`sudo -n true` → `password is required`). The 2026-06-04 decision §1
explicitly permits "*or equivalent local installation*", so every
toolchain was installed under `$HOME`:

| Recipe location | This-host location | Equivalent? |
|---|---|---|
| `/usr/local/go` | `~/.local/opt/go/` | yes (PATH-equivalent) |
| `/usr/bin/java` via `openjdk-17-jdk` | `~/.local/opt/jdk17/` (Temurin 17.0.19) | yes |
| `/usr/bin/mvn` via apt | `~/.local/opt/maven/` (3.9.16) | yes |
| `~/.cargo` via rustup | `~/.cargo` via rustup | identical |
| `dotnet-sdk-8.0` via apt | `~/.dotnet/` via `dotnet-install.sh` | yes (DOTNET_ROOT-equivalent) |

The decision file's "or equivalent" clause covers exactly this case.
PM may want to add a "no-sudo path" subsection to `dev-host-setup.md`
referencing the `~/.local/share/novetest-toolchains.sh` pattern below
as a documented alternative — operational recommendation, not a
correction.

### Evidence B — CLI-level smoke (`uv run novetest run`) per adapter

Three smokes run from isolated fixture copies under
`tests/manual-test-workspace/host-equip-2026-06-04/` (gitignored):

#### ✅ Go adapter — full CLI envelope

Fixture: `gotest-basic`. `novetest run .` returned `ok: true` with the
full Run Record (`TestAdd`, `TestAddSubtests`,
`TestAddSubtests/commutative`, all `outcome: passed`). First end-to-end
CLI confirmation of the go-test adapter on this box.

#### ⚠️ Cargo adapter — CLI vs adapter-direct discrepancy (new observation)

The adapter's own integration tests pass (`test_cargo_basic_*` and
`test_cargo_coverage_*` — see Evidence A). But the **CLI-level smoke**
on the same fixture produces `adapter-unparseable-output`:

```json
{
  "errors": [{
    "code": "adapter-unparseable-output",
    "message": "cargo nextest exited 4 without starting any test (likely build failure); stderr tail: ... Starting 0 tests across 2 binaries (3 tests skipped) ... error: no tests to run\n(hint: use `--no-tests` to customize)\n"
  }],
  "ok": false
}
```

Direct `cargo nextest run` on the same fixture works correctly:
3 tests run, 2 passed, 1 intentionally failed.

Reproducer (one command per line, after sourcing the PATH file):

```bash
source ~/.local/share/novetest-toolchains.sh
cd tests/manual-test-workspace/host-equip-2026-06-04/cargo-sut
cargo nextest list                                           # 3 tests discovered
cargo nextest run                                            # 3 run, 2 pass, 1 fail (correct)
uv run --project /home/yjshin/dev/aispace/Nove-Test novetest run .   # adapter-unparseable-output
```

Two plausible root causes (Run team's call to determine):

1. nextest 0.9.137 default behavior around `--no-tests` differs from
   earlier 0.9.x; the adapter may need `--no-tests=pass` (or
   equivalent) in its invocation to stay stable across the supported
   nextest range.
2. The CLI orchestration passes a target/filter (derived from the
   positional `.`) that nextest evaluates to "no tests match",
   resulting in `3 tests skipped` at the filter layer. The
   integration test uses `target_expression="", target_type="workspace"`
   and bypasses this code path.

The misleading message "*(likely build failure)*" is itself a flaw —
stderr clearly shows `Finished test profile … target(s) in 0.17s`,
i.e. build succeeded. The `adapter-unparseable-output` heuristic is
misfiring on a legitimate "all tests filter-skipped" outcome.

**Per the 2026-06-04 decision §5**, this does NOT retroactively block
cargo (cargo shipped under the v1 exception). It IS valuable
information for the cargo-trigger backlog (`2026-05-29-cargo-adapter-v1-without-rust-e2e.md`
§3 closure triggers) and for whoever next touches the cargo adapter.

#### ⚠️ JUnit adapter — reproduces the queued hotfix's symptom

## Takeaways for PM

1. **Host status flipped from "partial verifier" to "full polyglot
   verifier".** All four currently-merged adapters (pytest, jest, go,
   cargo) plus JUnit (under hotfix) and dotnet (pre-merge) can now be
   exercised end-to-end on this box. The 2026-05-29 cargo finding's
   `partial` verdict was directly attributable to this box's missing
   Rust; with the host equipped that gap is closed for all future
   cycles.

2. **The 2026-06-04 equip-and-exercise decision is now operationally
   satisfied on this box.** Integration suite skip rate proof:
   `9 passed, 1 failed (queued P1), 2 skipped (Gradle OR clause)`.
   The CLI-level smoke gate fires on every adapter; cargo's CLI
   discrepancy is recorded above; JUnit reproduces the known P0 the
   hotfix targets.

3. **One new defect candidate**: the cargo adapter's CLI-orchestration
   path emits `adapter-unparseable-output` on the canonical fixture
   while the adapter-direct integration test passes the same fixture.
   This is genuinely new — the 2026-05-29 verification couldn't reach
   this code path on a Rust-less host. Recommend Run team writes a
   focused integration test that exercises the CLI orchestration path
   (not just `run_cargo()` directly) so the discrepancy surfaces in
   CI, then patches either the adapter's nextest invocation or the
   "build failure" heuristic per §4.B of `engine-adapters.md`.

4. **Operational note for `scripts/dev-host-setup.md`**: the existing
   recipe is sudo-based throughout. A "no-sudo / user-home"
   alternative subsection (referencing the
   `~/.local/share/novetest-toolchains.sh` PATH-file pattern used
   here) would let future Manual Test sessions equip without
   interactive privilege elevation. Optional; PM's call.

5. **`~/.local/share/novetest-toolchains.sh` is the single source of
   truth** on this host for which versions are installed and where.
   If PM ever wants to bump a floor or test against a different
   ceiling, that file is the surgical edit point.
