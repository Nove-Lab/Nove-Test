## What changed and why (CEO-readable narrative)

The prior cycle (`f8f8d93`) shipped the .NET / xUnit v2 adapter — the 6th and last native engine for Nove Test's MVP. Manual Test verdict-failed it on the equipped host: **D1 — `novetest run --coverage` silently no-op'd** on freshly-copied user projects.

Root cause: the adapter's `_probe_coverlet_version` ran `dotnet list <csproj> package --include-transitive --format json` **before** `dotnet test`. That command requires `obj/project.assets.json` (a `dotnet restore` artifact). On a fresh project copy with no `obj/`, the command returned a `problems[]` entry instead of `frameworks[]` data, the parser returned `None`, and the adapter treated Coverlet as absent — so `--coverage` got silently dropped from the argv with no envelope-level warning. From the user's perspective, `--coverage` did nothing and there was no indication why.

This hotfix ships three fixes:

| Fix | What | Where |
|---|---|---|
| **F1a** | `_ensure_csproj_restored` runs `dotnet restore <csproj>` BEFORE the probe — but **only on the coverage path** (non-coverage runs don't pay the restore cost) | `src/novetest/run/adapters/dotnet_adapter.py:726` (helper) + `:377` (call site under `if collect_coverage and not is_xunit_v3:`) |
| **F1b (partial)** | When `--coverage` requested AND probe returns `None` even after restore, populate `metadata.coverage_unavailable_kind = "coverlet-absent-or-stale"` + `metadata.coverage_unavailable_message` with a user-actionable hint | `dotnet_adapter.py` metadata population path. **NOTE**: full envelope top-level `warnings` projection is a CROSS-TEAM follow-up filed as `questions/run-team-2026-06-06-envelope-warnings-projection.md`. This slice ships the Run-team-scope partial. |
| **F1c** | New integration test `test_coverage_run_on_fresh_fixture_with_no_prior_restore` explicitly asserts no `obj/` precondition + post-fix `coverlet_version == "6.0.2"` — so any future regression that re-introduces the dependency is caught structurally, not by host-state luck | `tests/integration/run/test_dotnet_coverage.py` |

Also: 10 new unit tests (6 × `TestPreRestore` + 4 × `TestEnvelopeSafetyNet`) pinning the helper's behavior at the mock-subprocess level.

## Critical edges worth probing (Manual Test's discretion)

These are not pass/fail asserts — they're known-shape "go look at this" hints for Manual Test's exploratory pass. Findings here become PM-disposition items, not verdict-blockers.

1. **`coverage_outcome.kind == "unavailable"` even when cobertura XML IS emitted (Cap-3)**. On JUnit's analogous `novetest run --coverage` path, `coverage_outcome.kind` resolves to `"fact-set"` with a populated summary. On the .NET path here — even with a fully-populated `artifact_paths["coverage_xml"]` cobertura on disk — `coverage_outcome.kind` is `"unavailable"`. This is an empirical observation on the merged tip; it's NOT a regression introduced by the hotfix (the original `f8f8d93` ships the same Coverage engine path). Hypothesis: the Coverage engine has a JaCoCo XML derive path but no Coverlet cobertura derive path yet — `derive_coverage_facts` may need a dotnet/cobertura adapter to round out the contract. Worth surfacing for the Coverage team or PM. **Not a hotfix-1 defect; informational.**

2. **`coverage_outcome.kind == "unavailable"` is also what Cap-4 shows.** Cap-4 (F1b safety-net path) and Cap-3 (full coverage path) both report the same `coverage_outcome.kind`. The user has no way to distinguish "coverage requested but Coverlet missing" from "coverage successfully collected but Coverage engine doesn't know how to derive facts yet" purely from `coverage_outcome` — they have to look at `metadata.coverage_unavailable_kind` for the disambiguation. This is consistent with #1 and reinforces the case for a Coverage-team follow-up.

3. **F1b's user-readable message wording.** The `coverage_unavailable_message` text is shipping verbatim as captured in Cap-4. Read it as a user encountering it for the first time — does the "add `<PackageReference Include=\"coverlet.collector\" Version=\"6.0.2\" />` to your test .csproj" hint give enough actionable detail? Should it mention `--include-prerelease` or alternative installation paths? Manual Test's user-experience judgment carries weight here.

4. **The `runsettings` artifact contents.** Cap-3 confirms `artifact_paths["runsettings"]` is populated. Per the amended Coverlet decision §3 (2026-06-05), the runsettings template keeps `<PerTestCoverage>true</PerTestCoverage>` for forward-compat even though the XPlat-data-collector path empirically ignores it (aggregate-effective-default). Worth opening the file and verifying the content matches the decision's pinned template; if Coverlet 6.0.x ever starts honoring `PerTestCoverage` in XPlat mode, the same runsettings would auto-promote per-test data without code change.

5. **Per-test data absence in the cobertura XML.** Per the amended decision §3 + R4, .NET coverage on v1 is aggregate-only — the cobertura emitted by Coverlet 6.0.2 in XPlat mode has no per-method-per-test tagging. Manual Test can `xmllint --xpath` the cobertura to confirm no per-test breakdown elements appear. This is by-design; the verification doc records it for completeness. Phase 4 SBFL on .NET will operate in `failure_proximity` mode per R4, not the per-test SBFL formulas.

6. **Restore-time behavior on cold NuGet cache vs warm.** Cap-3 ran on this host with the NuGet cache warmed from prior cycles (`~/.nuget/packages/coverlet.collector/6.0.2/` was already populated). On a truly cold cache (CI first-run scenario), `dotnet restore` may take 5-30s. The F1a helper sets a 300s timeout; Manual Test can simulate by `rm -rf ~/.nuget/packages/coverlet.collector` before Cap-3 and observe the restore-cold path. NOT a verdict criterion; useful telemetry.

7. **`engine_version == dotnet SDK version`, not xUnit version.** The convention across all six native adapters is `engine_version = the native tool's version` (mvn version for JUnit-Maven, gradle version for JUnit-Gradle, etc.). For .NET that's the dotnet SDK. The actual xUnit version sits at `metadata.xunit_version`. This is by-design per the engine-identity rule in decision `2026-05-25-supported-engine-matrix.md` and is correctly observed in Cap-1 through Cap-4.

8. **Cap-3's `coverage_xml` path lives under `run/artifacts/run_<ULID>/native/TestResults/<GUID>/`** — both the run ULID and the Coverlet-generated GUID are part of the path. The `<GUID>` segment is Coverlet's own per-collector-invocation identifier; Manual Test can verify with `find run/artifacts -name "coverage.cobertura.xml" -type f` to confirm a single file lands per `--coverage` invocation (not zero, not multiple).
