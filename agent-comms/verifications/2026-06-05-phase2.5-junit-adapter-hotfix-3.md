### Cap-6 — Hotfix-3 init-script lands under store (hermetic)

After Cap-5, on disk:

```
$ find /tmp/junit-gradle-probe/.novetest -name "init-ignore-test-failures.gradle"
/tmp/junit-gradle-probe/.novetest/run/artifacts/run_<ULID>/native/init-ignore-test-failures.gradle

$ cat <that path>
// Auto-generated by novetest JUnit adapter (hotfix #3, 2026-06-04).
// Makes Test tasks report failures via JUnit XML without failing the
// build, so :jacocoTestReport can run after :test. Safe to delete after
// the run — recreated per run under <artifact_dir>/native/.
allprojects {
    afterEvaluate { project ->
        project.tasks.withType(Test).configureEach {
            ignoreFailures = true
        }
    }
}
```

The init-script is **per-run** under the artifact dir (not `/tmp`), making
the run hermetic (concurrent runs don't collide on a shared init-script)
and postmortem-discoverable (sits alongside `stdout.log` / `stderr.log` /
`coverage/jacoco.xml`). The argv passes `--init-script <that path>` to
the Gradle invocation, and **only** when `collect_coverage and has_jacoco`
is true — non-coverage runs see neither the init-script nor `--continue`
(which hotfix-3 also removed, as it didn't help with dependent tasks).

## Critical edges worth probing

1. **Maven 3.8.7 vs floor 3.9.** Verification host has Maven 3.8.7 (apt-noble
   default — the only version pre-authorized by `.claude/settings.json`).
   Matrix floor (`decisions/2026-05-25-supported-engine-matrix.md`) says
   3.9. All hotfix-3 fixes work on 3.8.7; the floor mismatch is captured
   as Run team open item #1 (see "Anything that wasn't obvious" §1). If
   Manual Test's host has Maven 3.9+, prefer that; otherwise 3.8.7 is
   load-bearing-equivalent for the JUnit adapter's argv (`-B`,
   `-Dmaven.test.failure.ignore=true`, Surefire 3.x goals).

2. **Gradle version coverage.** Run team verified on Gradle 8.5; the
   previous (failed) Main Branch gate ran on Gradle 8.14.5 — both 8.x
   minor versions exercise the same `Test.ignoreFailures` semantic, but
   if Manual Test's host is on Gradle 9.x, the
   `testRuntimeOnly("org.junit.platform:junit-platform-launcher")`
   declaration in `junit-gradle-basic/build.gradle.kts:36` (hotfix-2
   forward-compat fix) becomes load-bearing. Pin Gradle 9 coverage if
   available.

3. **`--init-script` mechanism collateral.** The init-script applies
   `ignoreFailures = true` to ALL `tasks.withType(Test)` across
   `allprojects`. On multi-module projects, this affects every module's
   test task. If a future multi-module fixture lands, verify that
   per-module test failures are still reported via JUnit XML (just not
   raising the task-level exit) and the normalizer still derives
   `status="failed"` correctly per module.

4. **Init-script file cleanup.** The init-script is written per-run and
   never explicitly deleted. It naturally co-locates with the run's
   other artifacts and is discoverable post-mortem. This is intentional
   per Run team handoff §4 ("Why under artifact_dir, not /tmp: keeps
   the init-script postmortem-discoverable"). If `novetest` ever adds
   a `clean` verb or artifact-pruning policy, the init-script falls
   under the same lifecycle as `stdout.log` / `coverage/jacoco.xml`.

5. **Exit-code-becomes-0 invariant pair (Maven + Gradle now both apply).**
   Both `_aggregate_junit_status` in `normalizer.py:736-757` and the
   CLI exit-code mapping in `cli/output.py:12-17` derive `status` from
   parsed JUnit XML, not from `native_exit_code`. Hotfix-2 and hotfix-3
   make both build tools emit `native_exit_code=0` even when tests fail
   (Maven via `failure.ignore`, Gradle via `Test.ignoreFailures`); the
   CLI maps to exit 3 (`EXIT_USER_TESTS_FAILED`) via the XML-derived
   status. The native_exit_code is preserved in metadata for postmortem
   visibility. This invariant pair MUST hold — if Manual Test sees
   exit 0 from the CLI on the canonical failing-test fixture, that's a
   regression.

6. **Console Launcher SHA-256 + size pin.** Cap-G above. If the pin
   drifts (vendored asset replacement or PyApp packaging regression
   per R4), the engine returns `engine-misconfigured`. The pin is
   load-bearing for supply-chain integrity (Decision
   `2026-06-03-junit-console-launcher-vendor.md`).

7. **CLI-level smokes execute, not skip.** Per the binding equip-and-
   exercise §1, on the equipped host the `test_cli_smoke_run_emits_envelope`
   tests MUST execute (not skip via `shutil.which("mvn")`/`("gradle")`).
   If they skip, the verification is `partial` (not `passed`). On the
   pre-merge gate host they all executed — total 1034 passed includes
   both smokes.

8. **Maven `-Dmaven.test.failure.ignore=true` argv ordering.** The flag
   MUST precede the `org.jacoco:jacoco-maven-plugin:report` goal in the
   reactor argv. Pinned by `TestMavenCoverageArgv.test_failure_ignore_flag_present_with_coverage_and_jacoco`
   (`idx_flag < idx_goal` assertion). If a future refactor reorders the
   argv composition, this canary catches it before the runtime regression.

## Anything that wasn't obvious during merge

1. **Maven 3.8 vs 3.9 floor mismatch persists** (Run team open item #1).
   Both Run team's gate and Main Branch's gate ran on Maven 3.8.7 (the
   apt-noble default; the only Maven the `.claude/settings.json`
   pre-authorization permits installing). The matrix floor in
   `decisions/2026-05-25-supported-engine-matrix.md` is 3.9. The adapter
   doesn't actually use any Maven-3.9-specific syntax (only `-B`,
   `-Dmaven.test.failure.ignore=true`, Surefire 3.x goals — all
   3.8-compatible). PM should decide: (a) bump the matrix floor to 3.8
   (preferred — fewer moving parts), OR (b) keep 3.9 floor and amend
   `scripts/dev-host-setup.md §5` to install via Apache binary tarball
   (currently blocked by auto-mode classifier — would need CEO
   authorization). This is a PM call, not blocking the merge.

2. **F2 fix shape declared "Fix-D" outside brief's A/B/C enumeration.**
   Brief listed Fix-A (two-pass), Fix-B (init-script `finalizedBy`),
   Fix-C (fixture edit). Run team's diagnostic walk showed A and B both
   fail on Gradle 8.x because the task-graph semantic for dependent
   tasks doesn't change with `--continue` or `finalizedBy`; C is
   rejected by brief on user-project-assumption grounds. The actual
