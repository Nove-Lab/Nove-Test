## Critical edge cases worth probing

These are not blockers; document outcomes in Findings even if non-fatal.

**Edge 1. Hatchling deviation from brief §1.1.** The brief prescribed `[tool.setuptools.package-data]`; the team correctly noted this is a Hatchling project and used `[tool.hatch.build.targets.wheel.force-include]` instead. Cap-2 pins the deviation as **wire-correct** (wheel ships the three files). This is informational only — PM may want to amend the brief verbatim for future vendored-asset slices. Not a defect.

**Edge 2. PyApp binary blob extraction (R4 closure across three platforms).** The unit-gate R4 test (`test_importlib_resources_resolves_vendored_jar`) pins `importlib.resources` resolution on a regular install. The PyApp binary extraction (Linux x86_64, Linux aarch64, macOS universal2) is **Release team's smoke** at handoff, NOT this slice's source test. If Release team reports R4 fires on any platform, the documented fallback (extract jar to process-local tempdir on first use) requires a reactive code addition; flag in Findings if you can probe a PyApp binary today.

**Edge 3. Gradle wrapper absent from fixture.** Handoff followup #6. `tests/fixtures/projects/junit-gradle-basic/` ships without `gradlew` (no system gradle in the team's dev environment to invoke `gradle wrapper`). Manual Test on an equipped host can commit the wrapper + `gradle/wrapper/gradle-wrapper.jar` (~60 KB) as a separate slice; the wrapper would let the Gradle integration test run without a system `gradle` install. Not a defect — handoff explicitly out-of-scope.

**Edge 4. Multi-JDK projects (toolchains / `--release` per source set).** Out of scope per handoff §"Out of scope". The adapter assumes a single-JDK invocation. If you probe a multi-JDK project (e.g. one module on JDK 17, another on JDK 21 via Maven toolchains), expect undefined behavior — file a Findings entry with the observed envelope shape so the next hardening cycle has a pin to fix against.

**Edge 5. OTR (open-test-reporting) XML preference.** `engine-adapters.md §3` mentions OTR as preferable over Surefire XML when present; v1 parses Surefire XML only. If a project ships OTR alongside Surefire, the adapter still reads Surefire and ignores OTR. Not a defect — explicit followup #4 in handoff.

**Edge 6. `--per-test-class` opt-in absent.** Handoff followup #3. Surefire `forkMode=perTestClass` would give per-test-class coverage attribution at 2-5x runtime cost. Currently aggregate-only per D1. Confirming this is **expected behavior**, not a regression — if Localization downstream needs per-test attribution, it degrades gracefully to `sbfl_aggregate` mode.

**Edge 7. SHA-256 pin update flow.** If a future cycle bumps the Console Launcher to 1.12.x, three places must update in the **same commit**: (a) `_vendor/__init__.py` `LAUNCHER_JAR_FILENAME` + `LAUNCHER_VERSION` + `LAUNCHER_JAR_SHA256`; (b) `_vendor/THIRD_PARTY_NOTICES.txt` prose; (c) the jar binary itself. R4 mitigation test (`test_importlib_resources_resolves_vendored_jar`) re-verifies the pin at every test run — a missed pin update breaks CI immediately.
