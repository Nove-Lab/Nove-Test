- **근거**: `src/novetest/coverage/cobertura_parser.py:246` — parse_cobertura_xml의 루프(cobertura_parser.py:237-246)가 `for class_el in package_el.findall("classes/class")`로 각 <class>마다 FileCoverage를 만들고 `files_by_path[file_coverage.file_path] = file_coverage`(:246)로 dict에 대입한다. 병합 로직이 전혀 없다. _build_class_file_coverage는 `class_el.find("lines")`로 그 클래스에 속한 라인만 읽는다(:317-338). 즉 파일당 여러 <class>가 있으면 나중 것이 앞 것을 완전히 덮어쓴다. 기존 테스트/픽스처는 파일당 <class> 1개만 다룬다. :574의 test_multi_file_input_overwrites_same_file_path_last_wins는 '여러 XML 파일'의 last-wins만 검증하며 '단일 XML 내 동일 filename 다중 <class>'는 미검증.
- **실패 시나리오**: C#은 한 소스 파일에 다중 타입(클래스+중첩클래스, 여러 class, partial 동반 타입 등)을 두는 것이 관용적이다. - **권고**: files_by_path[path]에 이미 항목이 있으면 덮어쓰지 말고 executed_lines/missing_lines를 합집합 병합(그 뒤 executed 우선 규칙으로 중복 정리)하고 per-file summary를 재계산하도록 변경. 멀티 XML(per-test forward-compat) last-wins 의도와 충돌하지 않게, 병합은 '단일 파일 파싱 세션 내 동일 file_path' 기준으로 적용. 파일당 <class> 2개(동일 filename) 회귀 픽스처 추가. **(예상 크기: 1-cycle)**
- **검증 노트**: :237-238 이중 루프와 :244-246의 병합 없는 직접 대입, _build_class_file_coverage의 per-class 라인 판독, _resolve_workspace_relative의 filename-기준 경로 결정을 모두 확인 — 동일 filename 다중 <class>가 반드시 충돌하며 기존 테스트가 이 경우를 미검증. 침묵 데이터 손실 + AI 소비자 오결론으로 H 적정.

### ANA-03 [M] replay만 *Unavailable을 하드에러(ok:false, exit4/2)로 승격 — 다른 파생엔진은 모든 불가용을 data(ok:true, exit0)로
- **근거**: `src/novetest/cli/app.py:1730` — coverage.show/diff(app.py:898-905, 921-928), regression.compare/latest(app.py:995-1002, 1019-1026), localization(app.py:1214-1222)는 불가용 여부와 무관하게 항상 `ok=True`, EXIT_OK로 방출하고 불가용은 data.*_outcome.kind=="unavailable"로만 표현. 그러나 replay의 _build_replay_envelope(app.py:1730-1775)는 REASON_ENGINE_NOT_READY/REASON_TARGET_MISSING→ok:false, EXIT_ENGINE_MISSING(4); REASON_ORIGINAL_NOT_FOUND→ok:false, EXIT_USAGE(2); 나머지만 ok:true, exit0. 즉 같은 `ReplayUnavailable` 타입이 사유에 따라 error 채널과 data 채널로 갈린다. envelope 계약(cli/output.py:46-63)에는 '읽기 동사 vs 실행 동사' 구분자가 없어 사전 판별 불가.
- **실패 시나리오**: 에이전트가 coverage/regression/localization에서 '파생-사실 동사는 ok:true를 주고 나는 data.*_outcome.kind만 읽으면 된다'고 일반화하면 replay에서 오작동한다. 엔진 언인스톨 상태에서 `novetest replay <id>`는 ok:false+exit4+errors[0].code=`replay-engine-not-ready`를 주는데, 형제 동사들에선 exit/errors를 아예 안 보던 파서라 비정상 종료를 치명적 transport 오류로 오해하거나, 반대로 exit만 보던 파서는 coverage/regression의 exit0 불가용을 '성공적 데이터 있음'으로 오판.
- **권고**: 계약 문서(replay.md/orchestration.md)에 '실행형 동사(run/test/replay)는 엔진 부재를 exit4 에러로, 순수 읽기형 동사(coverage/regression/localization)는 불가용을 exit0 data로 낸다'는 규칙을 명문화하거나, replay도 불가용을 data 채널로 통일하고 exit는 별도 필드로 노출. 최소한 4개 파생엔진의 불가용 채널 정책을 한 표로 고정. **(예상 크기: 1-cycle)**
- **검증 노트**: 형제 읽기형 동사 5곳의 무조건 ok=True/EXIT_OK와 _build_replay_envelope의 사유별 ok/exit 분기, 상수(EXIT_OK/USAGE/ENGINE_MISSING, replay-<reason> code)를 모두 확인 — 봉투는 well-formed이나 계약에 읽기형/실행형 구분자가 노출 안 돼 소비자 사전 판별 불가. 데이터 손상 아님 → M.

### ANA-04 [M] 파서 간 num_statements 의미 불일치: Istanbul은 '문(statement) 수', 나머지 3개 네이티브 파서는 '라인 수'
- **근거**: `src/novetest/coverage/istanbul_parser.py:146` — istanbul_parser.py:146 `num_statements = len(statement_map)`(문 개수)로 summary를 만들지만, executed_lines/missing_lines는 statementMap의 start.line 기준 라인 집합(:144-145)이다. 반면 jacoco_parser.py:338·cobertura_parser.py:416은 `num_statements = len(executed_lines)+len(missing_lines)`(라인 수), lcov_parser.py:389는 `da_total = len(block.da_hits)`(고유 DA 라인 수)로 라인=문으로 취급한다. 따라서 jest FactSet만 `summary.num_statements`(문 수) ≠ `len(executed_lines)+len(missing_lines)`(라인 수)라는, 다른 모든 파서에서 성립하는 불변식을 위반한다.
- **실패 시나리오**: 한 줄에 문이 여러 개인 JS 파일(예: `let a=1; let b=2;` 3문이 1라인)을 jest로 커버하면 num_statements=3, executed_lines+missing_lines=1로 벌어진다. num_statements/percent_covered를 '라인 커버리지'로 해석하거나 파서 불변식(num_statements==라인수)을 가정해 executed_lines 길이와 대조하는 소비자는 jest에서만 어긋난 값을 얻는다. 또 표시 계층에서 병치될 때 jest의 문-기준 %와 다른 엔진의 라인-기준 %가 의미가 달라 오도.
- **권고**: num_statements의 계약 의미를 스키마 수준에서 '문 수'로 확정하고 라인기반 파서들이 이를 라인수로 채우는 관행을 문서/필드로 명시하거나(예: num_lines 별도 노출), 반대로 istanbul도 라인수로 통일. 최소한 CoverageSummary 문서에 엔진별 num_statements 기준(문 vs 라인)을 명시해 소비자 오해를 차단. **(예상 크기: 1-cycle)**
- **검증 노트**: 4개 파서의 num_statements 계산식을 모두 확인 — jest만 문-기준이라 다중-문 라인에서 불변식 위반. 단 models/coverage_fact_set.py:43-49가 CoverageSummary를 coverage.py totals 미러링('문 수')로 명시하므로 Istanbul이 오히려 계약 충실하고 라인기반 3개가 근사하는 쪽 — 프레이밍은 역전이나 수치 의미 불일치 핵심은 참이라 confirmed.
