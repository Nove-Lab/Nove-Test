# Worklog

Cross-agent handoff log. Newest entry on top. One entry per session that touches `src/` or `tests/`.

See `CLAUDE.md` → "Multi-Agent Worklog Harness" for the rules. The `PreToolUse` hook at `.claude/hooks/check-worklog-before-commit.sh` blocks `git commit` of `src/`+`tests/` changes that do not stage this file.

**Entry format:**

```
## <YYYY-MM-DD> — <phase> / <area>
- Landed: <what merged, with file paths>
- Verified: <command(s) run and result>
- Left open: <unfinished slice or follow-up>
- Gotcha: <surprise that future-you needs to know; or "none">
- Next: <suggested next step for the next agent>
```

When this file exceeds ~200 lines, move entries older than the current phase into `design/archive/worklog-<phase>.md` and link from the top.

## 2026-05-21 — phase2.5 / jest-adapter-windows-npx

- Landed: fixed the jest adapter being unrunnable on Windows. Root cause (verified via Release's analysis `questions/release-team-2026-05-20-jest-adapter-windows-npx.md`): the readiness probe resolves `npx` via `shutil.which` (honours `PATHEXT` → finds `npx.cmd` → readiness PASSES), but `run_jest` then exec'd the **bare name** `"npx"` via `create_subprocess_exec`; Windows `CreateProcess` only appends `.exe` to a bare name (never `.cmd`/`.bat`), so `npx` was not found → `FileNotFoundError` → misleading `AdapterInvocationError("npx not found on PATH")`. `src/novetest/run/adapters/jest_adapter.py` — `run_jest` now resolves `npx` via `shutil.which("npx")` up front (the SAME resolution the readiness probe uses, so guard and exec can never disagree again); `None` → typed `AdapterInvocationError(kind="missing-binary")` raised explicitly rather than relying on a downstream `FileNotFoundError`. New pure helper `_npx_launcher(npx_path, *, windows)` builds the launcher prefix: POSIX → `[npx_path]` (resolved absolute path, exec'd directly); Windows → `["cmd", "/c", "npx"]`. The Windows path runs the `.cmd` batch shim through `cmd.exe` because `CreateProcess` cannot execute batch files at all (only PE binaries); `cmd.exe` itself resolves fine (`CreateProcess` appends `.exe`). The **bare** name `npx` (not the resolved `.cmd` path) is handed to `cmd` deliberately — `cmd` applies `PATHEXT` to find `npx.cmd` (same resolution `shutil.which` confirmed), and a bare first token sidesteps `cmd /c`'s leading-quote-stripping rule that would corrupt the command line when later args (e.g. a `--outputFile=` path) contain spaces. The `except FileNotFoundError` handler is kept as a narrow fallback (TOCTOU race; missing `cmd.exe`) with an updated message. POSIX behaviour unchanged except `argv[0]` is now the resolved absolute path instead of the bare `"npx"` (functionally identical — `execvp` resolved the bare name to the same file). Tests: `tests/unit/run/adapters/test_jest_adapter.py` — new `_stub_npx_on_path` autouse fixture stubs `shutil.which` → a fake path so the up-front resolution succeeds on a Node-less box (without it every `run_jest` test would raise `missing-binary` before reaching the stubbed subprocess); `test_argv_includes_target_expression` updated to expect the resolved path as `argv[0]`; the old `test_missing_npx_binary_raises_typed_error` split into `test_unresolvable_npx_raises_typed_error` (`shutil.which`→None → typed error before any spawn) + `test_launcher_exec_failure_falls_back_to_missing_binary` (FileNotFoundError from the spawn itself still → `missing-binary`); two new pure-function tests `test_npx_launcher_posix_uses_resolved_path` + `test_npx_launcher_windows_wraps_in_cmd`.
- Verified: `uv run pytest -q tests/unit tests/integration` → 337 passed + 3 skipped (the 3 skips are the Node-dependent jest integration tests, expected on a Node-less box; +3 net unit tests from this slice). `uv run mypy` → clean (52 source files, `--strict`). NOT verified on a real `windows-latest` box — see "Left open".
- Left open: **No `delivery-phasing.md` DoD bullet closes** (defect fix, not a DoD bullet). CI currently SKIPS Windows jest (the `ci-node-win-fallback` `runner.os != 'Windows'` guard from commit `c350e5c`), so this fix is NOT yet exercised on `windows-latest`. Definitive signal = the companion Release guard-removal task PM dispatches after this handoff; the post-removal CI run on `windows-latest` confirms it. The fix mechanism PM needs for that task's scope: **POSIX unchanged; Windows routes `npx` through `cmd.exe /c npx`** (NOT a direct `npx.cmd` exec — `CreateProcess` cannot run batch files).
- Gotcha: the headline subtlety the task flagged as MANDATORY — resolving `npx` to its absolute `.cmd` path and passing THAT to `create_subprocess_exec` is **insufficient** on Windows: `CreateProcess` (which `subprocess`/`asyncio` use with `shell=False`) cannot execute `.cmd`/`.bat` files at all — it raises `WinError 193` (`%1 is not a valid Win32 application`). Batch files are interpreted by `cmd.exe`, never launched directly. So the fix MUST go through `cmd.exe /c`. Second subtlety: do NOT pass the quoted resolved `.cmd` path as the first token after `cmd /c` — when other args are quoted (spaces in temp paths), `cmd /c`'s documented rule strips the leading+trailing quote of the WHOLE line if the first char is a quote, mangling the command. A bare unquoted first token (`npx`) avoids that entirely; `cmd`'s own `PATHEXT` resolution finds `npx.cmd`. Confidence: high on the `CreateProcess`-can't-run-`.cmd` fact and the `cmd /c` quote rule (both long-standing, documented Windows behaviour); the only thing unverified is a live `windows-latest` run, which is gated behind the Release guard-removal task by design.
- Next: (1) PM dispatches the companion Release task to drop the `runner.os != 'Windows'` guard in `ci.yml` so jest runs on all 9 CI cells again; the post-removal `windows-latest` run is the definitive verification of this fix. (2) If a future adapter execs another Node `.cmd` shim (e.g. a `vitest`/`pnpm` launcher), reuse `_npx_launcher`'s pattern — that would be the 3rd instance motivating a shared `run/adapters/_node.py` launcher helper.
